# AI 第一版

文档保持全宽，AI 入口为文档画布底部居中的悬浮修改框，宽约 560px，窄屏自适应。位置随原生导航、属性侧栏和窗口大小调整，原生批注保留。输入框只填写补充要求，可留空；主按钮为“按批注修改”。不展示聊天记录、模式切换或手动选区入口。

左侧导航为“大纲、搜索、会话”三个 Tab，保留原生大纲和搜索行为，支持左右方向键、Home/End 切换。会话页逐次记录补充要求、“读取批注 → 生成修改 → 写入修订”的进度、修订数量、未处理批注与可展开的“修改详情”。执行时打开会话页；切换其他 Tab 不清空任务记录，原生大纲刷新不会抢走会话页。最近 20 次执行保存在当前页面内存，刷新后重置，不写浏览器持久存储。

中间悬浮框只保留输入、发送、停止、收起和“会话”入口，不再展示进度、结果或修改详情。收起保留输入与运行任务，展开不会重复提交；完成信息在左侧会话页查看。

修改结果直接以原生修订呈现在文档中，用户在原生审阅功能中接受或拒绝。未涉及的内容和格式保留，替换片段内部的复杂字符格式仍需核对。适配器依赖当前自编译 Collabora 的同源 iframe，升级后须重跑验收。

## 服务端配置

在 wopi 容器环境中配置 `AI_BASE_URL`（含 `/v1`）、`AI_MODEL` 与 `AI_API_KEY`。API Key 通过 Kubernetes Secret 注入，禁止写入仓库或浏览器。私有 HTTP 模型网关需显式设置 `AI_ALLOW_HTTP=1`；默认要求 HTTPS，拒绝上游重定向。前端不提供任意模型地址覆盖。

`POST /api/ai/revise` 需要现有门户登录，校验同源、文件存在、正文大小与字段类型。共享实验室身份具有现有知识库权限；这不提供多租户隔离。最多同时处理四个模型请求，每次 60 秒超时。只返回建议，不在服务端改写文档。错误响应不回传上游异常正文。取消停止浏览器等待；已发给模型的请求可能继续执行至超时。

未配置时显示明确配置错误，不能视为真实模型联调通过。

## 验证

运行 `python3 -m unittest discover -s apps/office-portal -p 'test_*.py'`。浏览器验证脚本使用独立上传的合成文档，不改写用户已有文档；模型结果采用明确的测试替身，模型真实调用须另行配置验收。下载 DOCX 核对 `w:ins`、`w:del` 与修改正文。部署遵循现有 main 自动构建发布流程，保留 Secret、PVC 和其他三个渲染服务。

## MiniMax M3

选择 `AI_BASE_URL=https://api.minimax.io/v1` 与 `AI_MODEL=MiniMax-M3`，`AI_API_KEY` 引用服务器 Secret。代理为该模型启用 `reasoning_split=true`，只使用正文 `content`，不返回或写入 `reasoning_content`；使用 `max_completion_tokens=8192`，截断输出仍拒绝应用。

官方接口参考：https://platform.minimax.io/docs/api-reference/text-openai-api 。模型权限与计费由所用 MiniMax API Key 决定，配置完成后必须使用合成文本做真实请求验收。

服务器部署补丁：`deploy/k8s/wopi-ai-minimax.patch.json`。先在 office-lab 创建 `office-ai-minimax` Secret，字段为 `AI_API_KEY`，再应用补丁。补丁只包含引用，不包含密钥。

`python scripts/verify-ai-editor.py --real-model` 使用真实模型测试独立合成文档；默认仍使用模型测试替身。真实模式会产生少量模型调用费用。

当前部署使用中国区 `https://api.minimaxi.com/v1`，对应用户提供的中国区 API Key。国际区与中国区须使用各自匹配的凭据。`deploy/k8s/wopi-ai-egress.json` 仅向门户放行官方域名在部署时解析出的 IP 的 TCP 443；不移除现有隔离。MiniMax DNS 地址变动后需重新核对并更新 IP 白名单。

## 默认：原文与批注驱动的自动修订

默认工作方式为“修改文档”。点击“按批注修改”，或填写补充要求后发送，即从当前 Writer 会话读取全文和全部未解决批注，不需要手动选择原文。以导出 HTML 中的批注标记关联对应段落，把原文段落、批注意见、段落关联和补充要求组成服务端 prompt。无法确定范围的批注交给模型说明，不能凭空定位。

原文每批最多约 12000 字、200 段；每个段落完整处理，不截掉原文。长文档只压缩非编辑背景为最多 6000 字的段落摘录，依次发送所有原文批次。当前上限为 20 万字、2000 段，单段 12000 字，未解决批注最多 100 条且总长不超过 16000 字；超限明确报错。背景摘录不是语义摘要，不保证涵盖远距离推理所需的全部上下文。

模型返回结构化的原文片段与替换文字。服务端校验精确匹配、段落归属、不重叠、批注 ID 及输出完整性；客户端再核对全文与批注快照，通过原生搜索唯一定位每处原文，开启修订后从文末向前局部替换，并请求保存。无需再点击“接受建议”，用户最终在原生审阅中接受或拒绝修订。未涉及的段落和样式不整篇重建，替换片段内部的复杂字符格式仍需核对。

生成期间文档或批注变化时停止写回；同文重复、跨段或不能精确定位的片段拒绝自动写入。应用期间编辑器暂时不可交互，可从悬浮框停止剩余步骤；其他协作者仍由原生协同系统管理，每步写入前再次核对快照，并检查前序改写是否导致下一个目标变得不唯一。已经成功写入的修订不自动回滚，异常会报告已确认的数量。批注原文继续保留，审阅状态按下述生命周期处理。

旧的聊天与选区接口保留兼容，不作为当前界面入口。

验证：`python scripts/verify-ai-revise.py --real-model` 在正式页面新建合成文档，加入两条批注，直接执行默认工作流，并下载 DOCX 验证两处插入/删除修订、批注、未修改段落及标题格式。`--local-assets` 仅替换浏览器候选资源；无 `--real-model` 时使用明确测试替身。`--long-document` 验证分批完整覆盖，`--changed-document` 验证快照变化阻止写入（后两项配合测试替身）。


## 批注与修订的生命周期

`ai_review.py` 将当前关联及最近 500 条状态审计写入文档数据目录下的 `.ai-review.sqlite3`，使用事务和任务租约避免多个客户端重复修改；不保存模型密钥或原文正文。修订以作者、时间、类型、原生描述的指纹关联，不能依赖重开后会重新编号的临时修订 ID。相同指纹不能唯一区分时保持待核对，不自动解决。

模型必须为每条相关批注返回 `comment_results`（complete / partial / unhandled）。缺失完成报告按部分完成或未处理对待，不能仅凭 `comment_ids` 存在判定全部完成。生成修订后状态为待审阅，默认不再交给模型重复处理；刷新和其他用户会话继续使用服务端状态。

原生逐条/全部接受、拒绝以及管理修订窗口中可明确识别的接受/拒绝操作，通过操作前后的原生修订表确认实际移除的条目。所有关联修订确认接受、该批注要求确认全部完成后，才调用原生解决批注操作。只接受一部分时仍待审阅；存在拒绝时，待剩余修订审阅完成后恢复待修改。部分完成或未处理的要求始终保留未解决，不覆盖原作者、文字或讨论。讨论串还有未完成回复时，不提前解决主批注。

人工解决优先；人工重开后，无待审阅修订可重新交给 AI，有待审阅修订时先审阅现有修改。撤销恢复关联修订时恢复待审阅并重新打开由 AI 自动解决的批注。无法确认的消失、复杂撤销重做、外部修改及未完成关联的写入，保持待核对，不能当作接受。服务端互斥和动作认领避免两个窗口重复切换同一条批注的解决状态。

“会话”页显示待审阅、待修改、待核对和已解决状态。内容仍在原生批注中，随 DOCX 保存；离线导出后再作为新文件上传不继承原文件的服务端关联。

### 引擎配置

需要启用 `--o:per_document.redlining_as_comments=true`，否则原生修订表会返回空数组，即使 DOCX 内存在修订。两个现有编辑器首次配置分别使用 `deploy/k8s/collabora-ai-review.patch.json` 和 `deploy/k8s/collabora-wordmac-ai-review.patch.json`，只追加公开配置开关，保留镜像和其他参数；补丁应在确认尚未包含该参数时应用一次。回退时从部署备份恢复原参数。门户自动发布保留现有引擎配置。

### 验收

`python scripts/verify-ai-revise.py --local-assets --review-lifecycle` 使用真实原生审阅和本地真实状态存储代码，模型为测试替身，覆盖刷新跳过、部分接受、全部接受、拒绝、人工解决/重开、部分完成和撤销。`--local-assets --cross-user` 使用两个独立浏览器会话验证跨用户接受后同步，并核对原作者。正式环境去掉 `--local-assets` 并使用 `--real-model` 做实际模型联调；审阅全流程默认使用测试替身以验证确定的部分完成分支。
